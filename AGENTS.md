# AGENTS.md

Lab for comparing third-party agent skill bundles and synthesizing new skills
from the strongest parts. Markdown skills, Python 3 with PyYAML, and Bash.
OpenSpec is the fixed artifact system for the synthesized pipeline.

## Project map

- `analysis/` - inventory, comparison, synthesis, coverage, and eval evidence.
- `docs/` - `workflow.md` (stage graph and GitHub mapping),
  `agent-files.md` (persona spec), and `open-tasks.md` (project resume point).
- `skills/` - source of truth for the eleven synthesized skills.
- `.opencode/skills/` - generated mirror OpenCode discovers: project skills plus
  the six `openspec-*` workflow skills.
- `.opencode/commands/` - `opsx-*` commands generated by `openspec init`.
- `openspec/` - repo-level OpenSpec root (`spec-driven` config, specs, changes).
- `scripts/` - inventory generator and skill sync.
- `vendor/` - cloned upstream bundles, untracked, never edited.
- `bundles.txt` and `sync.sh` - upstream bundle list and sync.

`skills/` is the source of truth for the eleven synthesized skills.
`.opencode/skills/` is generated; do not edit it directly. The mirror also
carries the six `openspec-*` workflow skills written by
`openspec init --tools opencode`; refresh those with `openspec update`, not by
editing them or by hand-copying them into `skills/`.

## Commands

| Command | What it does |
|---|---|
| `./sync.sh` | Clone or fast-forward every bundle in `bundles.txt` into `vendor/`. |
| `python3 scripts/inventory.py` | Regenerate `analysis/inventory.md` from `vendor/`. Fails if a skill is unmapped. |
| `./scripts/sync-skills.sh` | Copy `skills/` into `.opencode/skills/`. Leaves `openspec-*` entries in place. |
| `openspec update` | Refresh the generated `openspec-*` skills and `opsx-*` commands. |

## Git commit messages

Follow `git-workflow`. Use `<area>: <imperative, lowercase summary>` with areas
`skills`, `workflow`, `analysis`, `docs`, `scripts`, `eval`. The body explains
why.

## Skill invocation

Load a skill when it has even a slight chance of applying, including supporting
skills. Prefer loading it and deciding it was unnecessary over reconstructing its
guidance from memory. A skill's description lists triggers; do not wait for the
user to name the skill.

When two skills could apply, prefer this project's stage or supporting skill over
a global generic skill.

## When adding or changing a synthesized skill

- Edit `skills/<skill-id>/SKILL.md`, then run `./scripts/sync-skills.sh`.
- Follow the `skill-forge` skill. A behavior-shaping change needs a baseline or
  micro-test record, or an explicit debt note in `analysis/evidence/README.md`.
- Keep skills environment-agnostic. For the five stage skills, tracker operations,
  the approval marker, the review destination, and workspace/push policy belong
  to agent files, not skills. The supporting skills are invoked directly by a
  human or an agent mid-task; they read the repository's instructions and fall
  back to their defaults. OpenSpec remains fixed.
- Update `README.md`, `analysis/synthesis.md`, and `analysis/coverage.md` when
  the skill set or boundary changes.

## When adding or updating a vendored bundle

- Add the name and URL to `bundles.txt`, then run `./sync.sh`.
- Never edit files under `vendor/`; they are upstream copies.
- Map every new skill in `scripts/inventory.py`, then rerun the inventory. The
  script exits non-zero until the mapping is complete.

## When updating the analysis

- Categories are editorial and live in `scripts/inventory.py`; `analysis/inventory.md`
  is generated, not hand-edited.
- `analysis/comparison.md` is a historical cross-bundle comparison.
  `analysis/synthesis.md` and `analysis/coverage.md` describe the current set.
- Keep claims traceable to a vendored file, the repo, or recorded evidence.

## When changing stage routing or loop rules

- Update `docs/workflow.md` for transitions, verdicts, and delivery examples.
- Keep the skill verdict (`pass | needs_revision | blocked`) and its reason
  semantic. Tracker operations, labels, `gh` commands, review state, and PR
  mechanics belong to the persona's agent file, not to skills.
- If a skill's interaction contract changes, run `./scripts/sync-skills.sh` and
  record evidence or debt in `analysis/evidence/README.md`.

## When running an eval

- Read `docs/open-tasks.md` and `analysis/evidence/README.md` first. The former
  lists pending project work; the latter records what is verified per skill.
- One skill at a time, per `skill-forge`. Do not batch untested skills.
- Do not present an unverified skill as passing; check
  `analysis/evidence/README.md` for the current status.
