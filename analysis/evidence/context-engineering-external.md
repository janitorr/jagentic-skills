# context-engineering: external skill efficiency evaluation

Model: `deepseek-v4.1-flash` (`opencode-go`, default variant).

Status: **negative as a loadable skill; positive only as an applied practice.**
54 read-only runs across three real repositories, two task types, three
conditions, and three repetitions. Loading the skill increased tokens and tool
calls with no measured quality gain. A compact project map, which is what the
skill recommends but does not produce, reduced tokens, tool calls, files read,
and wall time. The skill fired on its own in 0 of 36 non-skill runs.

The skill is the global `context-engineering` skill installed at
`~/.config/opencode/skills/context-engineering/SKILL.md`, matching the
addyosmani `context-engineering` entry recorded in `analysis/synthesis.md`. It
is not one of this repository's ten synthesized skills.

## Question

Does loading `context-engineering` make an agent cheaper or faster on real
repository work? Specifically: fewer tokens, fewer tool calls, fewer files read,
and less wall time, without losing answer quality.

A second question isolates the skill's advice from its prose: if the project map
the skill recommends is supplied up front, do the same metrics improve?

## Conditions

| Condition | Prompt |
|---|---|
| `control` | The task only. |
| `skill` | The task plus "load the `context-engineering` skill with the skill tool and apply its guidance." |
| `primed` | The task plus a compact project map: repo layout, spec/doc locations, canonical files, commands. No skill text. |

The `primed` arm is the skill's practice applied mechanically. The map was
hand-built from each repo's `AGENTS.md`, `README`, and directory listings, not
generated by the skill. It is an upper bound on "advice applied," not a measure
of the skill text.

All runs used the same model and provider as the top Model line, the same
read-only instruction, and the same answer cap (250-300 words). No files were modified.

## Repositories and tasks

| Repo | Code task | Documentation/spec task |
|---|---|---|
| `janitorr/nagger` | Trace one-shot completion from HTTP route to SQLite write. | Reconcile the morning-report OpenSpec, `USAGE.md`, and code; report mismatches. |
| `janitorr/mittens` | Trace `mittens_set` to SQLite and list files for a nullable `Tags` field. | Reconcile persistence/MCP/REST specs and `setup/SETUP.md` with code; report stale claims. |
| `darrenhinde/OpenAgentsControl` | Explain agent discovery, installation, and loading. | Reconcile `CONTEXT_SYSTEM_GUIDE.md`, registry docs, `registry.json`, and `install.sh`. |

Two studies, nine cells each, three repetitions per cell: 54 runs.

## Measurement

Per-session metrics came from OpenCode's SQLite store (`session_v2` and the JSON
in `session_message`), not from self-report:

- `tokens_input`, `tokens_output`, `tokens_cache_read`, `tokens_cache_write`;
  `tokens_total` is their sum, `tokens_billable` is input plus output.
- Tool-call count by tool name, `read` calls, and distinct `read` paths.
- Wall time from session creation to last update.
- Skill call: `content[].type == "tool"`, `name == "skill"`, `input.id ==
  "context-engineering"`.
- Repo containment: every tool input was checked for the three clone paths; all
  54 sessions stayed in their assigned repo.
- A five-key rubric per task checked that the answer named the requested
  artifacts. It is a guardrail against "cheaper by doing less," not a fine
  quality score.

Token totals include cache reads. Cache reads are cheaper than fresh input but
still reflect context volume and turn count, so `tokens_billable` is reported
separately.

## Results

### Skill loading and firing

- 18 of 18 `skill` runs called `skill` with `id: context-engineering` and
  received the full 16,805-character body.
- 0 of 36 `control` and `primed` runs loaded any skill. On these tasks the skill
  never fires on its own.

The skill body is 353 lines, 2,288 words, 15,486 characters, about 3.9k tokens
by `chars / 4`. Every forced load pays that cost before doing any work.

### Answer quality

All 54 answers were substantively correct on the requested rules. Rubric means
(control / primed / skill): code 1.00 / 0.98 / 1.00; docs 0.91 / 0.96 / 0.96.
The only rubric misses were peripheral: whether a run also noticed that
`CHANGELOG.md` still said report `schemaVersion` `"4"` while the spec, USAGE,
and code said `"5"`. That was not a requested finding. There is no evidence the
skill improves or degrades answer quality on these tasks.

## What the numbers say

1. **Loading the skill is a net cost.** It adds a tool turn and about 3.9k
   tokens, then changes search behavior only weakly. Forced use was +23% tokens
   on code tasks and +26% on docs tasks, +44% tool calls on code tasks, and
   +3-18% wall time. It did not reduce files read: code reads rose 30%, docs
   reads fell 10%.

2. **The recommended practice works.** Supplying the project map cut tokens
   13% (code) and 37% (docs), tool calls 13% and 26%, reads 20% and 36%, and
   wall time 16% and 36%. The win comes from removing discovery: primed runs
   start at the spec, USAGE section, or target source instead of `ls`, `glob`,
   and broad `grep`.

3. **The skill does not mechanize its own advice.** It tells the reader to
   build a rules file and a hierarchical summary, but ships no generator,
   template fill, or script. AGENTS.md reads did not increase under the skill
   (2 of 9 code control runs touched it, 2 of 9 skill runs, 0 of 9 primed).
   The prose did not reliably become behavior.

4. **The repositories already have the context the skill recommends.**
   Nagger and Mittens have detailed `AGENTS.md` files with "Where To Look
   First" sections. OAC has `CONTEXT_SYSTEM_GUIDE.md`, a 191-entry
   `components.contexts` registry, and installer validation. The skill's
   Level 1 advice ("write a rules file") is already banked; loading the skill
   again cannot bank it twice.

5. **The skill is not aimed at these tasks.** Its description targets starting
   a session, declining output quality, switching tasks, and setting up a
   project. It does not claim to help trace a call path or reconcile a spec.
   That is why it never fired. The evaluation therefore measures what happens
   if a user or harness loads it anyway, not what happens when it is selected
   appropriately.

## Static audit of the skill

The 353-line document is a reference essay, not a procedure:

- 17 `##` sections, including a full `CLAUDE.md` template, a generic project
  map template, a context-budget section, an MCP server table, confusion
  management, anti-patterns, a rationalization table, red flags, and a
  verification checklist.
- Many lines are no-ops for a capable agent: read the file before editing,
  run tests, ask when requirements are ambiguous, keep task-critical content
  last.
- The templates are illustrative, not executable. There is no script to
  produce the map, detect the rules file, or measure context use.
- The document itself is 3.9k tokens. Loading it to save context is
  self-defeating for short tasks; its own anti-pattern table warns about
  context flooding.
- The useful part is small: read the rules file, make a project map, load only
  the relevant spec section, prefer pointers over full documents. That part
  fits in a short checklist and is what the `primed` arm tested.

## Threats to validity

- Three repetitions per cell, one model, default sampling. The direction is
  consistent, but the exact percentages are not precise.
- Read-only exploration only. No edits, builds, tests, or multi-turn work. A
  context skill could matter more when a task spans many turns.
- The primed map was built by the evaluator from the repo's own docs. It is an
  upper bound on "practice applied," not something the skill produced.
- Token totals include cache reads; cache reads are cheaper but grow with turn
  count. Billable input plus output is shown separately.
- One docs/primed run fetched 13 external pages and is a tail outlier. Medians
  and paired ratios are used; the run is not deleted.
- OAC agents often used `shell` instead of `read`, so distinct-file counts are
  not comparable across repos. Tool calls are.
- The sample is context-mature. Nagger and Mittens ship detailed `AGENTS.md`
  files, and OAC ships a context system and registry. A repo with no rules file
  or navigation docs could benefit more from the skill's setup advice; that
  case was not sampled.
- The skill's intended output, a better `AGENTS.md` or project map, was not
  scored for quality. Only the efficiency of consuming context was measured.
  That is the remaining open question.

## Verdict

**Do not ship `context-engineering` as an always-available task skill.** It
does not fire on repo work (0/36), and when forced it costs more tokens, more
tool calls, and more time without improving answers.

**Do keep the practice.** A compact, repo-specific project map produced the
only measurable win: 13-37% fewer tokens, 13-26% fewer tool calls, 20-36% fewer
files read, and 16-36% less wall time, with equal answer quality.

The practical form is a generator or template that writes a short `AGENTS.md`
or project map once, not a 3.9k-token essay loaded per task. If the skill is
kept, narrow its trigger to "set up context for this repo," "write or revise
AGENTS.md," and "output quality is degrading," and delete the generic
rationalization, MCP, and restartable-session sections.
